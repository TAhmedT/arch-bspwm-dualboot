# Хранилище и виртуальные машины

Шаблоны ВМ и Kubernetes-кластер не создаются. Этот профиль готовит Arch как
рабочую станцию KVM и оставляет отдельное место под ваши будущие машины.

## Установить KVM/libvirt

В ASUS UEFI включите **SVM Mode** (обычно Advanced → CPU Configuration).
TPM и Secure Boot оставьте включёнными; IOMMU для обычных ВМ не требуется.
Единственная RTX 3060 Ti остаётся у рабочего стола, GPU passthrough не настраивается.

В установленном Arch:

```bash
cd /opt/arch-bspwm-dualboot
sudo bash install.sh virtualization
```

Скрипт проверит `/dev/kvm` и datasets, установит QEMU/KVM, libvirt,
virt-manager, OVMF и swtpm, добавит пользователя в `libvirt,kvm`, включит
локальную службу и стандартную NAT-сеть. Настройки существующих pools
не перепривязываются, конфликты служб требуют проверки.

Выйдите из сеанса и войдите снова, затем откройте **virt-manager**.
Подключение — **QEMU/KVM system (`qemu:///system`)**. ISO кладите в `/srv/iso`.
Диски ВМ храните в `/var/lib/libvirt/images`, чтобы они не тратили квоты
`/` и `/home`. NAT даёт выход в интернет и доступ с хоста к гостям;
другие устройства домашней сети не получают прямой доступ к ВМ.
Мост Ethernet можно настроить позже, если это действительно понадобится.

## Как менять распределение SSD без переразметки

```bash
sudo bash install.sh storage
```

Меню покажет состояние и предложит:

1. Посмотреть занятое и доступное место.
2. Изменить квоту системы, `/home`, ВМ или ISO.
3. Создать дочерний dataset для файлов диска отдельной ВМ.
4. Создать блочный диск zvol для подключения к ВМ.

По умолчанию `/` ограничен 96 ГиБ, `/home` — 160 ГиБ, все ВМ — 512 ГиБ,
ISO — 64 ГиБ. Около 96 ГиБ дополнительно удерживает `archpool/reserve`.
Физический ZFS-раздел занимает остальной SSD, но это **не отдаёт его целиком
системе или домашнему каталогу**: квоты останавливают запись в каждую область.

Например, увеличение ВМ до 600 ГиБ не копирует и не переразмечает данные.
Однако сумма квот может превысить физическую ёмкость: квоты не обещают, что
все области одновременно заполнятся до максимума. Проверяйте `USED/AVAIL`
и не доводите pool до заполнения. Снимки тоже занимают место в квотах.
Зарезервированное место не следует раздавать под обычные ВМ.

**Dataset** — файловая система/каталог. Для `lab01` меню создаст
`archpool/vm/lab01` с собственным лимитом, точкой
`/var/lib/libvirt/images/lab01` и записью в fstab. При создании ВМ в virt-manager
выберите файл raw или qcow2 внутри этого каталога. Для ZFS raw проще и
избегает второго слоя CoW; qcow2 тоже работает, но имеет свои накладные расходы.
Лимит дочернего dataset входит в общие 512 ГиБ `archpool/vm`.

**Zvol** — блочное устройство. Меню создаёт его без sparse-режима, с
резервированием размера и `volblocksize=16K`. Например, диск 40 ГиБ появится
как `/dev/zvol/archpool/vm/lab01`. В virt-manager: добавить/выбрать storage →
существующее блочное устройство → этот путь, шина VirtIO. ОС гостя сама
размечает этот виртуальный диск. Не выполняйте `mkfs` на физических дисках хоста.

Восемь zvols по 40 ГиБ зарезервируют примерно 320 ГиБ плюс накладные расходы,
внутри квоты ВМ. Sparse-файлы qcow2/raw могут выглядеть значительно больше
физически занятого места; overcommit дискового пространства требует контроля.
Увеличение виртуального диска также требует расширения раздела/ФС в госте;
меню автоматически не уменьшает и не переразмечает существующие диски.

## Ресурсы для 8 ВМ / Kubernetes

Ryzen 5 3600: 6 ядер / 12 потоков, RAM 32 ГиБ. Как начальный бюджет для
учебного кластера: 8 ВМ × 2 ГиБ RAM = 16 ГиБ и по 2 vCPU на ВМ.
16 vCPU — допустимое планирование поверх 12 потоков, а не дополнительные
физические ядра: одновременные сборки и тяжёлые workloads будут конкурировать.
Оставьте RAM хосту и ZFS ARC (его верхняя граница здесь 8 ГиБ).

2 ГиБ на control-plane — нижняя граница для небольшого кластера, а не запас
для Prometheus, Elasticsearch или CI. Для тяжёлых задач разумнее меньше ВМ
или больше RAM. Сначала можно поднять 1 control-plane и 2–3 workers, затем
расширить. Kubernetes HA внутри одного ПК полезен для практики, но не переживёт
отказ этого хоста или единственного SSD. Шаблоны и автосоздание кластера
в этот репозиторий не включены по вашему запросу.

## Снимки и сохранность ВМ

Снимок ZFS диска работающей ВМ без quiesce не гарантирует согласованность
БД и файлов гостя. Самый понятный первый вариант — штатно выключить нужную
ВМ, затем сделать снимок её отдельного dataset/zvol:

```bash
sudo zfs snapshot archpool/vm/lab01@before-change
sudo zfs list -t snapshot -r archpool/vm
```

У системного dataset и `/home` можно делать независимые снимки:

```bash
sudo zfs snapshot archpool/ROOT/arch@before-update
sudo zfs snapshot archpool/home@before-change
```

Снимок системы **не включает FAT32 `/boot`**. Не откатывайте корень вслепую
после обновления ядра: его modules, initramfs и подписанный UKI должны
соответствовать друг другу. Снимок диска ВМ также не содержит XML-конфигурацию
libvirt; сохраняйте её вместе с внешним бэкапом. Автоматический rollback и
удаление снимков здесь не выполняются.

Для ежемесячного scrub уже включён `zfs-scrub-monthly@archpool.timer`.
Scrub обнаруживает ошибки чтения/контрольных сумм; один диск не обеспечивает
восстановление всех повреждённых данных. Независимый бэкап нужен отдельно.
